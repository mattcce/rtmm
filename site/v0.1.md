# Loop 1

## Specification

For this first loop, designing an online, real-time matchmaking service that frequently accepts batched inputs and emits matched players into groups of 10 in a manner that optimises for turnaround time and rating deltas is an appropriate first level.

The inputs will be simulated by means of a service injecting a number (with some variance) of enqueue requests at regular (again with some variance) intervals, simulating a load-balanced endpoint aggregating requests before submitting them all at once.

Each enqueue request consists of a few pieces of information vital to the overall problem:

- Request ID: a unique identifier for the specific enqueue request
- User ID: a unique identifier for the user wanted to be enqueued
- Skill Rating: a number defining the user's skill rating at the time of request

### Request Stream

For simplicity, we consider enqueue requests to be binding; the user cannot dequeue themselves and can only be dequeued after they have been matched into the game.

The simulator will inject a large batch of requests at regular intervals with jitter, sampling from the skill rating distribution, to be defined.

The skill rating distribution we now define to be $cal(N)(1000, 200)$, mimicking chess' Elo system.

The requests will be provided in JSON.

### Output and Validation Stream

The matchmaker will output (batching allowed) matched players into a validator process. This process will act as the outgoing boundary for this project. We will use the validator process to run analytics on the quality of our matchmaker.

### Offline Analysis

As a separate target, we will want both the simulator and validator to output logs that we can use to run analysis at a later time.

### Out-of-Scope

The following features are intentionally deferred to Loop 2:

- **Reservations (starvation prevention).** Tickets in lease contention for too long cannot escalate to a reservation FIFO queue. In Loop 1, contended tickets cycle directly back to the ready queue as `ReadyPriority::Contended`.
- **WaitGraph (directed bipartite lease contention DAG).** Contention is stored as a simple per-bucket `Vec<Contended>` without edge tracking. When a lease is released, all contenders in the window are flushed without per-blocker resolution.
- **Backpressure.** I/O channels (`crossbeam_channel::unbounded`) and ringbuf buckets (`bucket_capacity: 1000`) have no flow control. Overflowed requests are silently dropped.
- **Queue overflow policy and segmented buckets.** Each bucket uses a single bounded `ringbuf`. No deferred/on-hold sub-structure exists — posts during a lease land in the same ringbuf and become visible after release. Dynamic queue sizing and segmented bucket queues are deferred.

## Conceptual Design

### Estimated Time to Matching

A restricted analysis will be performed to keep the problem tractable. Assume we require $N$ players all within an SR window of $xi plus.minus delta$. This is equivalent to a single player at $xi$ SR waiting for $N$ other players to be within $delta$ SR away from them, in order to form a match.

A naive MM algorithm may wait for the first player at $xi$ SR to queue, and thereafter wait for $N$ more players within $xi plus.minus delta$ to approach. Let requests stream in at some rate $Lambda$, and assume that these requests are sampled from a normal distribution $R tilde cal(N) (mu, sigma^2)$. The probability of any one drawing being within the desired range is therefore

$ p = PP(xi - delta ≤ R ≤ xi + delta). $

In one time unit, $Lambda$ requests enter; of these, we expect $p Lambda$ requests to be within the range desired. This is obtained from the binomial mean of $B(Lambda, p)$.

We can model this as a Poisson process with expected rate $lambda = p Lambda$. To model the time taken to $N$ hits, we use the Erlang distribution with $k = N$ and rate $lambda$. The mean of this distribution is $N slash lambda$, which yields us that we should expect to wait $N slash p Lambda$ time units before a match can be made.

### Optimal Delta Sizing

Given a tolerance of $T^ast$ (that is, the target expected wait time in time units, adjusted by considering how long a player is willing to wait before they get frustrated), the target $delta$ for a given $xi$ therefore must satisfy $N slash p Lambda <= T$.

For a given $xi, Lambda$, let

$ delta^* (xi, Lambda, N, T) = min_delta Lambda PP(abs(R - xi) <= delta) >= N/T. $

This gives the optimal delta sizing to find $N$ players near $xi$ skill rating in $T$ time units on average, with an inbound global enqueue rate of $Lambda$.

We will combine this target with local signals to determine the actual delta for each bin.

### Matchmaking Algorithm

The core matchmaking algorithm needs to highly parallelisable. There are tons of considerations to make, but the settled high-level algorithm is as follows.

We split the rating space into small bins (discretisation). To match players, we look over a contiguous collection of bins that correspond to an acceptable rating delta.

The rating delta can be increased or decreased dynamically based on player acceptability (match quality), time spent in queue, and also expected time to finding a match. A player should not wait too long in queue; we can assume that they would rather have a lower-quality match than no match at all, but we should still balance this by having some temporal tolerance as to how long we should wait.

We can make this precise with statistical modelling, by also considering expected time to finding a match: that is, how long we expect to wait before enough players at the right skill rating come in. In particular, we expect that players at tail ends will be more affected by this; there are much fewer players that are extremely high- or low-skilled.

**Scheduler**

The overarching scheduler maintains a queue of request tickets with the following information needed for each ticket:

- _Anchor Bin_: This is the main bin that forms the anchor skill rating around which we match.
- _Delta_: This is the spread around the bin with which we are allowed to look for matching.
- _Priority_: This is the abstract priority of the request, which decides when a ticket should be picked up relative to other tickets.

Bins are primarily prioritised for matching based on the time taken for the _least recent active request_ in said bin, among possibly other considerations.

The scheduler also maintains a _waiting lane_, which is used to delay tickets based on a _retry policy_ that we detail later. Tickets in the waiting lane are never scheduled until their delay has elapsed, at which point they are readmitted into the main scheduling queue, ready to be assigned.

Crucially, each bin may only be anchored in exactly one ticket at any given point in time. This ticket state model contains these states:

- ready: the ticket is ready to be assigned to a worker
- paused: the ticket is prevented from assignment by a timed delay
- assigned: the ticket is assigned and actively being worked on
- empty: the ticket is empty and does not need to be assigned (no requests)
- contended: the ticket is under contention
- reserved: the ticket is in reservation queue or has an active reservation

Tickets are retrieved from the scheduler, and this serves as the abstraction boundary between the scheduler and individual workers.

**Microstructure**

Workers will pick up tickets to work on from the scheduler.

In many bins near the centre of the rating distribution, when there are sufficiently many players, matching is a trivial problem as we can just keep matching any set of required players within the same bin, or we expect that we do not have to wait long for enough players to fill up the same bin. In such cases we do not resize at all.

In fact, we want to go even further and specify that the worker should keep trying to match the bin while they're already there, rather than free up the bin and possibly allow another worker or itself to take it over again, because of overhead costs. So we only release the bin when we have spent too much time there (global considerations: we may starve many bins if we have significantly more bins than workers) for hot bins.

We formalise this in the **Residency Policy**, which allows workers to hold on to tickets beyond just matching the first request and determines how long a worker is allowed to work on a ticket before it must release the ticket back with potential backoff.

For colder bins, the worker may not be able to find suitable matches at all within the same bin, so it will have to expand the delta to include more bins to increase the likelihood of matching. We call this the **Resize Policy**, which allows workers to increase and decrease the delta of a ticket based on how easy it is/was to find matches for that bin and delta.

Particularly, one of the important interactions is a resize and sleep system. After an expanding resize and still no matches can be made for that bin, we should not wait for a match or until the next resize. Instead, we should just send the ticket back into queue with some backoff to be looked at again later, when hopefully more players have joined those bins. The amount of backoff is affected by the updated priority of the ticket, which we formalise in the **Retry Policy**.

This specific structure avoids the problem of certain bins expanding and blocking other matches from being formed within bins in the same range. Essentially, we make a tradeoff between making very few players wait possibly much longer than make more players all wait longer.

Tickets are inherently coupled to the bins they reference (anchor and all bins within the delta). This will have important effects on memory allocation and synchronisation later.

**Residency Policy**

The residency policy allows a worker to extend its hold of a ticket for longer than a single matching, and determines how much longer it is allowed to hold that ticket.

As a base case, once a matching is no longer possible for that ticket, the residency policy requires that the ticket be freed immediately subject to resize and retry policy updating conditions.

The residency policy imposes a maximum budget on a ticket that allows a worker to keep working on the ticket and form more matches until it runs out of budget or matches.

**Resize Policy**

The resize policy updates a ticket's delta based on how easy it is/was to find matchings for that ticket in the previous matching session(s) for that ticket.

If the ticket was easy to match, then we potentially want to reduce the delta for that ticket until it is at minimum delta.

If the ticket was hard to match (no matches found in the last matching session), then we potentially want to increase the delta for that ticket until some maximum delta, in the hopes that after the increase there is a higher probability of finding a match.

**Retry Policy**

The retry policy updates a ticket's priority with backoffs according to the behaviour in the last matching session(s) for that ticket.

Once a ticket has been worked on, a base amount of backoff should be applied since either the ticket just ran out of budget (in which case we should let other tickets go) or it failed to match (in which case we should wait anyway for the bins to repopulate).

The amount of backoff applied may dynamically increase up to some fixed upper limit, with additional considerations for tickets that have been backed off for too long.

## High-Level Design

### Bastion Layer Separation

The safety invariants for matchmaking can be separated into two kinds: integral to the matchmaker itself, and externalisable. The externalisable safety invariants can be offloaded to a bastion layer that performs checks on incoming requests before submitting them to the matchmaker/queue.

For this loop, this bastion layer is not explicitly implemented. The generator is instead guaranteed to produce requests that satisfy preconditions and externalisable safety invariants required by the matchmaker.

### Input Subsystem Abstraction (Generator)

The input subsystem is an abstraction for a distributed system collecting enqueue requests. It produces batched inputs of enqueue requests that can be tuned as hyperparameters.

For simulation purposes, it generates batches of incoming requests sampled from a fixed skill rating distribution, and introduces jitter into batch interarrival times.

### Output Subsystem Abstraction (Validator)

The output subsystem is an abstraction for a distributed system receiving completed matches from the matchmaker.

For simulation purposes, it receives and grades the quality of the matches produced according to a predefined metric, producing live telemetry for observability purposes.

### Logging and Experiments

Both the generator and validator will dump logs in a portable format that can be used for further analysis at a later date. This will allow the running of distinct experiments and enable more robust analysis offline.

### Tickets

Tickets contain the following information:

- **Bin Index**
- **Delta**
- **Bookkeeping Information**

Tickets are conserved and transferred around to be held by various entities; each bin has exactly one ticket, and tickets cannot be created or destroyed except by a centralised issuer, only transferred.

A ticket is the unique transferable work capability for one anchor bin. Possession of the ticket authorises an entity to schedule or attempt acquisition for that bin and the full delta. Possession of a valid lease or reservation handle attached to the ticket authorises access to the corresponding delta. The ticket does not itself implement locking; locking remains the responsibility of the lease manager (the resource owner).

### Scheduler and Ticket Queue

The scheduler maintains three lanes:

- Reserved set: highest priority lane for reserved tickets that have just been freed from contention while holding a reservation
- Ready queue: priority queue for tickets ready to be assigned, with composite priority based first on highest total consecutive contention age up to present and then earliest active request in the bin anchored in that ticket.
- Waiting queue: priority queue for paused tickets that are forced to wait out a fixed period, with priority based on the earliest time they may be readmitted into the ready queue.
    - Note that since requests are batched, the waiting queue is flushed only when a new set of requests come in.
- Lease contention: array for tickets that cannot be currently worked on due to a part or whole of their delta being locked.
- Empty hold: hold of empty tickets

The scheduler gives out a ticket when asked for and expects it back in due time. It uses two algorithms, one for handling returned tickets, and one for handling ticket requests.

On ticket request by a worker:

- The reserved set is checked for any tickets requiring immediate assignment and promotion of reservation.
- The ready queue is then checked for an available ticket by priority.
- If there are no tickets, the worker is blocked until a new ticket arrives in the ready queue.

The scheduler is made responsible for handling lease acquisition.

**Lease Contention**

If a ticket is retrieved to be assigned and the scheduler fails to acquire a lease over the entire delta of the ticket, then a lease contention occurs and the ticket enters lease contention.

Lease contention uses another complex data structure: a wait graph. Conceptually, this is a bipartite directed acyclic graph where a directed edge from implies the source is blocking the target. More strongly, only active leases and reservations can block tickets.

When a ticket enters lease contention, all active leases are scanned, and the blocking leases and this ticket is added to the graph. This is time-bounded by the number of workers, which we expect to be small.

When a new lease is created, it is simply added to the wait graph with no outgoing edges. Scanning all contended tickets would take potentially too much time (bounded by number of bins); it is better to let the contended tickets cycle back into queue and back into contention if needed.

When a lease is released, the corresponding lease along with all outgoing directed edges (if any) in the wait graph are removed.

When a ticket no longer has any incoming directed edges, there are no leases left blocking it. It can therefore be removed from the graph and released back to the ready lane.

A contention age for each ticket is used to track the total amount of time a ticket has been in contention for since the last time it was acquired. This is used to tiebreak between tickets newly released from contention, and to prevent starvation (see below on Reservations). This is required because a ticket may repeatedly reenter contention or stay too long in contention, in which case we escalate to a different mechanism.

**Reservations**

*Note: while initially planned for Loop 1, this has now been deferred to Loop 2.*

Tickets in lease contention may starve due to other leases indefinitely holding onto some (if not all) of the bins required by the contended ticket. To solve this, we introduce a reservation system, that allows tickets that have stayed in contention for too long to directly reserve the resources they need. Tickets in the reservation system are said to be reserved.

The reservation system functionally applies FIFO with smart conflict resolution to advance tickets independent of those ahead of it in reservation. There is a reservation FIFO queue. When a ticket has stayed for too long in contention, it is escalated into reservations and enters the reservation queue.

At reservation time, the system will first check if it can make the ticket a reservation without jumping ahead of other tickets already in the reservation queue. If so, it will acquire the reservation immediately. The reservation is inserted into the contention wait graph to block other tickets from competing with the reserved ticket.

If no reservation can be made, then it is added to a FIFO reservation waiting queue. A linear sweep is made through this queue when we can acquire a reservation for any of the tickets in this queue. We can prove that we only need to scan on reservation promotion. A linear sweep is unlikely to pose significant performance concerns given that we expect reservations to be rare and waiting for reservations to be even rarer.

This allows disjoint reservations to be made without allowing a later-arriving ticket attempting reservation from jumping ahead younger tickets in reservation queue.

A special mechanism is used to assign the reserved ticket and elevate the reservation directly to a lease immediately when the contending lease is released. This prevents race conditions and competition with reserved tickets.

### Request Matrix

The request matrix is a complex data structure containing all of the active requests from users. As a whole, it is an ordered array of buckets each corresponding to a single bin in the rating space.

We distinguish between different request states:

- inactive: the request is not currently active (miscellaneous holder for inactivated requests, not used in this loop)
- served: the request has been served
- on hold: the request is for a locked bin and is accepted, but it is not eligible for assignment or matching until the bin unlocks
    - This happens when the bin is locked and currently being worked on, but new requests for that bin have come in. In such a case, the request is held in a deferred part of the bin and cannot be served until the next time the bin unlocks.
- active: the request has been posted to its bin and can be matched

Inbound requests admitted into the request queue are placed in their respective bins. Each bin maintains a FIFO queue of requests, so requests are processed in order within each bin. Also, each bin can quickly report the earliest active request within itself.

This data structure is fully owned by the scheduler.

Each bucket queue is fully synchronised, and can be read from and written to concurrently. However, when a bucket is allocated to a worker, the active portion is frozen. Later requests can be still ingested into bucket queues, but while a bucket is leased for active ground allocation, newly arrived requests for that bin are not eligible for matching until after the bucket is released.

### Workers

Workers will request jobs from the scheduler to execute, from a range of kinds of jobs. The job type expected to take up the most time is **ground allocation**.

Given a single delta of bins, the ground allocation algorithm collects any set of sufficient players and matches them. There are no other local considerations to make affecting match rating deltas, but it will attempt to respect the structure of the overarching system. It will allocate starting from the anchor bin, and expand outwards to adjacent bins until it reaches its full delta.

The residency policy allows a worker to hold onto a ticket and keep working on it as long as the anchor bin is not already empty of **active requests** (new requests arriving while the bin is leased are excluded from the current residency session). If the anchor bin is empty, no further matching attempts should be made.

This policy applies a constant matching budget that stops ground allocation once a number of matches has been formed successfully. The goal of this policy is to ensure fairness and provide response time guarantees; therefore, it need not be more complex than a fixed matching budget $B_0$.

This budget hyperparameter can be hand-picked; the only consideration is the tradeoff between response times and utilisation. We keep $B_0$ relatively low but high enough to benefit from avoiding the concurrency overhead.

Ground allocation also emits control signals that will be used to adjust the delta and timeout:

- number of successful allocations, $s$
- maximum bin distance from anchor in recent matching (measure of edge pressure), $e$
- termination condition (out of budget or out of matchings), $r$

Note that with this system, at most **one** match can be allocated per ground allocation run that has a delta wider than the anchor bin alone.

The resize policy operates using the provided control signals to target a delta to move towards. The exact optimal delta targeted is

$ min(Delta, delta^* (xi, Lambda, K_r, T_r)), $

where $K_r$ is number of players needed left for a single matching considering only the anchor bin, and $T_r$ is the remaining time budget (computed as the difference of the target waiting time and elapsed waiting time of the oldest request in the anchor bin), and $Delta$ is some global upper bound maximum delta.

This measure is adaptive and provides a reasonably expanding delta up to the global upper bound based on how long left the next player to match has to wait.

The control signals provide local guidance on whether or not to actually resize at a given point in time. Generally, if matching frequency is too low and the optimal delta is larger than the current delta, we bias towards expansion. If matching frequency is too high and the optimal delta is smaller than the current delta, we bias towards shrinking. Importantly, we do not expand or shrink based on only either local signals or optimal delta independently of each other.

The retry policy aims to backoff tickets that are known to not be matchable. There are two possible cases:

1. There are no active requests left in the anchor bin.
2. There are still active requests in the anchor bin, but no matches can be made out of the delta.

In the first case, we want to let the ticket fill up again before we commence matching. We handle this case specially: the ticket remains empty until new eligible requests arrive for that bin. There is no reason to hold up the ticket otherwise.

In the second case, it is fine to make the ticket wait despite it carrying older requests than in other bins, because the only way to match such requests is to wait for more requests to come in and hope that they are near enough to match. We combine this with delta sizing (resizing policy).

This policy operates on expected times to next matching. Specifically, we consider the expected time to matching $T_r = K_r slash p Lambda$, and pick $T_r$ to be the minimum backoff duration (minimum because the retry queue is only flushed when a new batch arrives, else the situation has not changed).

## Low-Level Design

### Repository Structure

Rust (and the surrounding ecosystem) is used as the main programming language for the entire project, including for the generator, matchmaker, and validator, primarily for performance reasons.

A single Cargo workspace is used, which supports multiple binaries. They will use the same shared library, but otherwise run independently of each other.

### Dependencies

- `crossbeam`
- `parking_lot`
- `prost`
- `ringbuf`

### Module Design

The main subsystems and entities are:

- Generator
- Validator
- Matchmaker
    - Internal subsystems: Request Matrix
- Scheduler
    - Internal subsystems: Ticketing, Lease Contention, Reservation

### Parallelisation

Parallelism and concurrent programming is primarily achieved with the `crossbeam` and `parking_lot` (and other associated libraries). 

The scheduler runs on a dedicated thread and hands out work to various worker threads, in a standard work thread pool model via message passing in an event-driven mechanism.

The optimal job to run is only known at the time of request; the scheduler does not effortfully predict and pre-assign jobs to threads nor does it prepare jobs in advance for worker threads. This means that it is preferable to not use a centralised job queue.

### Inter-Process Communication

The main mode of communication between the validator, matchmaker, and generator processes will primarily be via Unix domain sockets (Unix systems will be placed first-class), although we will generalise their interfaces to allow them to use any reasonable protocol.

### Encoding Protocol

For IPC, we do not expect to have to work around or consider schema evolution and instead prefer to work with fast encodings (fast to transmit and decode). The data emitted by the generator is consumed ideally almost immediately, and so is the data emitted by the matchmaker. The data will not persist long enough and it is not a general concern for the matchmaker to account for schema evolution.

Even for experiments, schema evolution is also generally not a concern.

### Random Sampling

To sample from a normal distribution, we use the fact that for any normally-distributed random variable $N tilde N(mu, sigma^2)$ and given the standard normal $Z tilde N(0, 1)$, we have

$ N = sigma Z + mu, $

so generating the standard normal is sufficiently.

For the standard normal, we combine the accept-reject method with the inverse-transform method.

We use the $Y tilde "Exp"(1)$ distribution, generated via the inverse-transform method, where given the cdf of $Y$,

$ F_Y (y) = cases(e^(-y) &quad "if" y >= 0\,, 0 &quad "otherwise",), $

randomly sample from the uniform distribution $U tilde U(0, 1)$, and via the inverse-transform method we have

$ F_Y^(-1) (U) tilde "Exp"(1), $

where $F_Y^(-1) (U) = -ln U$ is the inverse cdf of $"Exp"(1)$.

To generate the standard normal, we first consider the standard half-normal random variable $X = abs(Z)$, whose pdf is

$
	f_X (x) = 2 f_N (x) = 2/sqrt(2 pi) e^(-1/2 x^2).
$

We require $Y$ as it has the same support as this random variable. The standard normal random variable $Z$ can be recovered by flipping the sign of samples of $X$ randomly with probability $0.5$.

By the accept-reject algorithm, we sample $X$ and accept this sample, with probability

$ tau = (f_X (x_0)) / (c dot f_Y (x_0)), $

where $c$ is a constant that satisfies

$
(f_X (x)) / (f_Y (x)) <= c
$

over the support.

This value of $c$ is optimised at $x = 1$, which yields

$ c^* = sqrt((2e)/pi). $

While we can pick any value of $c >= c^*$, this specific value cancels out nicely with the rest of the expression for $tau$:

$
tau &= (e^(-x))/(sqrt((2 e) / pi) (1/sqrt(2 pi) e^(-1/2 n^2))) = e^(-1/2 (x-1)^2).
$

## Implementation

As with any new codebase, early implementation work tends to be a little messy, even if a great deal of planning has gone into it.

Features were implemented largely from the surface down, with a lot of scaffolding, temporary interfaces and simplifications, and revisions, made and revised along the way. The more interesting design decisions are highlighted in this section.

### Dependency Injection in Expected Singletons

While there are many accidental singleton classes, none of them are implemented as singletons. This is mainly to avoid committing to singleton structures, as none of them are semantically dependent on being singletons.

All of these classes are designed with dependency injection in mind: they will accept a configuration data structure at construction time to assemble themselves. This provides the abstraction needed and gives greater flexibility over hyperparameters.

### Request Bucket Queues

The request-bucket queue design is deliberately simplified for this loop. A more ambitious design was considered, including unbounded or segmented single-producer single-consumer queues, more careful airlocking semantics for inbound requests during residency, and principled backpressure handling. However, these concerns would substantially expand the scope of this loop and risk clogging up progress on the actual matchmaking process.

For this iteration, each request bucket instead uses the same bounded-capacity FIFO queue implementation via `ringbuf`. The capacity is hand-tuned uniformly across all buckets rather than derived analytically from the request distribution or scheduling model. Backpressure is explicitly ignored in this loop: if a bucket is full, newly arriving requests targeting that bucket are dropped.

This is a temporary scoping decision, not a final systems decision. Queue sizing, overflow policy, and better handling of dynamically growing or segmented bucket queues are all deferred to the next loop, where they will be treated as high-priority work.

### State Machines over Tickets

To track and pair state-specific bookkeeping information, a set of states and predefined transitions are used, involving operational wrapper types composing tickets and necessary bookkeeping.

This makes transient bookkeeping (related only to the current state of the ticket, and should be discarded after transitioning out or should be refreshed on transition in) directly tied to that state. Reasoning about correctness becomes significantly easier.

During state transitions, old wrappers are consumed and new wrappers are constructed. This forces the transition to use the old wrapper's information and forces new wrappers to be constructed with refreshed data.

This is in somewhat contrast to the usual State design pattern seen in higher-level OOP languages that rely significantly on subtyping polymorphism, runtime dispatch, and mutation to achieve the similar. The core principles have not changed, but the implementation shape has.

### Serialised Resource Leasing

To combat excessive complexity, a choice was made to move all leasing to the scheduler rather than let workers lease from a shared data structure themselves. This does mean that leasing is not parallelised, but this saves a huge amount of complexity when dealing with the massively complex lease contention system.

We expect this serialisation to have minimal cost; leasing is generally cheap. The actual work that needs to be parallelised (and what we will see the most benefit of parallelisation from) is ground allocation.

This is also stronger cohesion within the scheduler, as it avoids leaking scheduling mechanisms (like lease contention and reservations) and requiring many round-trips to acquire a job.

### Conventions

- `_raw` suffix for performance-related optimisations that cause temporary invariant violation, and must be restored by the caller.
- `_unchecked` suffix for optimisations that cause UB if caller does not satisfy the function contract.

## Evaluation

### Implementation Summary

The system is implemented as three Rust binaries communicating via Unix domain sockets with postcard-serialised, length-prefixed framed messages:

| Binary | Role |
|---|---|
| `generator` | Produces batches of `MatchmakingRequest` (request_id, skill_rating, submission_timestamp) sampled from N(1000, 200²). Sends via socket to matchmaker. |
| `matchmaker` | Runs scheduler (1 thread) + N ground allocator workers (default 4) + ingress/egress I/O threads (2). Implements ticket state machine (Empty→Ready→Contended→Assigned→Completed→Waiting/Ready/Empty), resize policy, retry policy, and residency-limited ground allocation. |
| `validator` | Receives batches of completed `MatchmakingAssignment` via socket. Computes rating variability penalty (α·Var + β·(max-min)²) and mean response time. |

### Metrics

Ran on M3 Pro, 4 workers, default config (50 buckets, delta_ceiling=5, bucket_capacity=1M):

| Metric | Value |
|---|---|
| Test suite | 96 tests (85 unit + 11 integration), 0 failures |
| Sustained load | 15 batches of 1M requests each in 15s |
| Actual matchmaker processing time | ~100ms wall time per 1M-request batch (matchmaker >99% idle) |
| Mean response time | 2.60s → 2.50s (declining as initial surge drains; dominated by distribution tail buckets) |
| Steady-state response time | ~2.50s per request on average |
| Rating variability penalty | ~1,883 (consistent across all batches) |
| Contention events | 0 across full 15M-request run |

### Observations

- **System is over-provisioned.** The matchmaker and validator can handle 100-1000x the tested load. The generator at 1 batch/second is the throughput ceiling.
- **Contention is a non-issue.** At steady state, delta stays small near the distribution centre. The 50-bucket discretisation provides sufficient player density for anchor-only matching in most bins. Reservations and WaitGraph (deferred to Loop 2) would add complexity without measurable benefit at this load.
- **Response time is tail-dominated.** The mean of ~2.5s is pulled up by extreme skill-rating bins at the edges of the distribution, where player density is low and delta must expand. Central buckets match within hundreds of milliseconds.
- **Rating variability penalty is stable at ~1,883.** This reflects the inherent spread of matching players from a N(1000, 200²) distribution within 50-SR buckets. Improving this would require tighter delta bounds or weighted matching (Loop 2 candidates).

### Profiling

Profiling was performed on the matchmaker binary (`cargo build --profile profiling`, which inherits `release` with `debug = 2, lto = false, strip = "none"`).

**Setup:** `generator_sustained` (100K requests/batch, 100ms delay = 1M req/s) running against 4 workers. `LOG_LEVEL=error` to eliminate log I/O as a profiling artifact.

**Tool:** macOS `sample $(pgrep matchmaker) 25 -file /tmp/profile.txt`. 25,423 samples per thread over ~25.4s.

**Results (10 threads):**

| Thread | % Active | Dominant function |
|---|---|---|
| Controller (main) | 0% | `std::thread::park` |
| Ingress listener | ~2% | `recvfrom` (socket read) |
| Egress sender | ~1.3% | `park`; minor `sendto` + `memmove` |
| 4× Workers | ~0.3% each | `crossbeam recv` (park); `run_allocation` ~250 samples total |
| Scheduler | ~1.1% | `crossbeam::Select::select` (99% idle in semaphore_wait) |

**Conclusion:** Total active CPU time across all threads is ~1.5%. The system is I/O-bound at this workload and well below saturation. Profiling at Loop 1 scale does not surface a meaningful bottleneck; `run_allocation` takes microseconds per match. At higher throughput, the expected limit is the serialisation + socket write path in the egress sender I/O thread. This is a known architectural constraint (single egress thread) and a natural candidate for profiling at Loop 2 scale.
